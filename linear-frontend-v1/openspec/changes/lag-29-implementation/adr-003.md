# ADR-003: Server-Sent Events over WebSocket for Real-Time Updates

## Context and Problem Statement

The keyboard module needs real-time updates when issues are modified by other users (e.g., status changes, assignments). The system must update the UI without requiring manual refresh. The communication is one-way: server → client.

## Decision Drivers

- Simplicity: The implementation should be straightforward
- One-way communication: Server sends updates; client does not send real-time data
- Browser support: Must work in all modern browsers
- Reconnection: Automatic reconnection on disconnect

## Considered Options

- Server-Sent Events (SSE)
- WebSocket
- Polling (setInterval + fetch)
- WebTransport

## Decision Outcome

Chosen option: "Server-Sent Events (SSE)", because it provides one-way server-to-client communication with built-in reconnection and browser support, without the complexity of WebSocket.

### Consequences

- Good, because simpler than WebSocket — no protocol upgrade needed
- Good, because built-in reconnection and event IDs
- Good, because works through HTTP proxies and load balancers
- Good, because native browser support (EventSource API)
- Bad, because one-way only — cannot send data from client to server
- Bad, because limited to text data (no binary)
- Bad, because no WebSocket-level multiplexing

### Confirmation

Verified by testing that issue updates are received in real-time via SSE and the UI updates without manual refresh. Fallback to polling can be added for environments that block SSE.

## Pros and Cons of the Options

### Server-Sent Events (SSE)

- Good, because native browser support (EventSource)
- Good, because automatic reconnection with Last-Event-ID
- Good, because simple HTTP-based — works through proxies
- Neutral, because text-only is sufficient for this use case
- Bad, because one-way only — requires separate channel for client→server
- Bad, because limited browser connection pool (6 per domain in HTTP/1.1)

### WebSocket

- Good, because bidirectional — can send and receive
- Good, because binary support
- Good, because lower latency than SSE
- Bad, because more complex — requires protocol upgrade
- Bad, because harder to debug through proxies
- Bad, because overkill for one-way communication

### Polling (setInterval + fetch)

- Good, because simplest implementation
- Good, because works everywhere — no special APIs
- Bad, because high latency —取决于polling interval
- Bad, because unnecessary network traffic when no updates
- Bad, because server load from frequent requests

### WebTransport

- Good, because modern protocol — low latency
- Good, because multiplexed streams
- Bad, because limited browser support (not yet universal)
- Bad, because requires HTTP/3
- Bad, because more complex than SSE
