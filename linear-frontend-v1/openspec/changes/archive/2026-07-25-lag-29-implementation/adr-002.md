# ADR-002: Zustand + localStorage for Offline-First Shortcut Customizations

## Context and Problem Statement

Users need to customize keyboard shortcuts (rebind keys). Customizations must persist across sessions and be available offline. The system must also support syncing customizations to the server when online, but this sync is not critical for the initial implementation.

## Decision Drivers

- Offline access: Users should be able to use custom shortcuts without network connectivity
- Persistence: Customizations must survive page refreshes and browser restarts
- Simplicity: The storage mechanism should be straightforward to implement and debug
- Future sync: The design should accommodate server-side persistence later

## Considered Options

- Zustand + localStorage (offline-first)
- Server-only storage (API calls)
- IndexedDB with sync
- Zustand + sessionStorage

## Decision Outcome

Chosen option: "Zustand + localStorage (offline-first)", because it provides immediate offline access with minimal implementation complexity, and the Zustand store can be extended to sync with the server later.

### Consequences

- Good, because customizations work offline and persist across sessions
- Good, because Zustand provides reactive state management out of the box
- Good, because localStorage is simple and well-supported
- Bad, because manual sync between localStorage and server is required
- Bad, because localStorage has a 5MB limit (sufficient for shortcut customizations)
- Bad, because potential inconsistency if user customizes on multiple devices

### Confirmation

Verified by testing that customizations persist after page refresh and are available in offline mode. Server sync can be added as a follow-up feature.

## Pros and Cons of the Options

### Zustand + localStorage (offline-first)

- Good, because offline-first — works without network
- Good, because simple implementation — no sync logic needed initially
- Good, because Zustand provides reactive updates
- Neutral, because localStorage is synchronous but fast enough for small data
- Bad, because manual sync needed for multi-device support

### Server-only storage (API calls)

- Good, because single source of truth — no sync issues
- Good, because multi-device support out of the box
- Bad, because requires network for customizations to load
- Bad, because latency on every customization load
- Bad, because offline mode is complex to implement

### IndexedDB with sync

- Good, because more storage capacity than localStorage
- Good, because supports structured data and indexes
- Bad, because more complex API than localStorage
- Bad, because async — requires more boilerplate
- Bad, because overkill for shortcut customizations (small data)

### Zustand + sessionStorage

- Good, because isolated per-tab — no cross-tab conflicts
- Bad, because lost on tab close — not persistent
- Bad, because doesn't meet the persistence requirement
